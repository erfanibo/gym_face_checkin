# سیستم لوکال تشخیص چهره برای پذیرش باشگاه

## معماری

```
دوربین USB  --cv2.VideoCapture-->  ترد پس‌زمینه (FaceEngine)
                                        |
                                        |-- شناخته‌شده؟ --> attendance_log
                                        |-- در صف اخیر؟ --> فقط last_seen_at آپدیت می‌شود (آنتی‌اسپم ۲ دقیقه‌ای)
                                        |-- ناشناسِ جدید --> عکس ذخیره + ردیف در pending_queue + broadcast روی WebSocket
                                        |
                                   SQLite (یک فایل، با قفل مشترک)
                                        |
                                   FastAPI (routes + /ws/queue)
                                        |
                                   پنل پذیرش (frontend/index.html)
```

نکتهٔ کلیدی: چون `cv2.VideoCapture` و `face_recognition` عملیات سنگین و بلاک‌کننده هستند، حلقهٔ دوربین در یک **ترد جداگانه** (نه یک تسک asyncio) اجرا می‌شود تا سرور FastAPI و اتصال‌های WebSocket هیچ‌وقت فریز نشوند. ارتباط این ترد با دنیای asyncio از طریق `asyncio.run_coroutine_threadsafe` انجام می‌شود (`face_engine.py`).

هر عضو می‌تواند تا `MAX_FACE_SAMPLES_PER_MEMBER` نمونه داشته باشد؛ `FaceEngine._match_known` همهٔ نمونه‌های همهٔ اعضا را یک‌جا با چهرهٔ فریم مقایسه می‌کند (نه فقط یک بردار به ازای هر نفر)، پس تشخیص به یک عکس ثابت از هر عضو وابسته نیست. اگر یک چهرهٔ ناشناس در صف انتظار در واقع یک عضو موجود باشد (مثلاً زاویه/نور متفاوت باعث «ناشناس» تشخیص داده‌شدنش شده)، اپراتور به‌جای «ثبت‌نام جدید» دکمهٔ «عضو موجود است» را می‌زند، عضو را از لیست انتخاب می‌کند، و آن چهره به‌عنوان یک نمونهٔ تازه به همان عضو اضافه می‌شود (`POST /api/queue/{id}/assign`) — بدون ساختن یک عضویت تکراری. این کار همیشه دستی است، چون یادگیری خودکار ریسک تقویت یک تشخیص اشتباه را دارد. اگر تعداد نمونه‌های یک عضو از سقف بگذرد، قدیمی‌ترین نمونه حذف می‌شود.

> اگر از قبل یک `gym_face.db` با نسخهٔ قدیمی‌تر پروژه دارید، نگران نباشید — `init_db()` هنگام استارت، ستون `event_type` را خودکار به جدول موجود اضافه می‌کند (migration idempotent، چیزی پاک نمی‌شود).

## بروزرسانی‌های اخیر

1. **رفع باگ آنتی‌اسپم** — قبلاً هر ردیف صف انتظار فقط با یک encoding ثابت (لحظهٔ ورود) مقایسه می‌شد؛ با کمی تغییر زاویه/حالت چهره در همون چند ثانیه، دیگه تطبیق پیدا نمی‌کرد و دوباره عکس گرفته می‌شد. الان هر ردیف چند نمونهٔ اخیر (`PENDING_DEDUP_MAX_SAMPLES`) نگه می‌داره و مقایسه با نزدیک‌ترین‌شون انجام می‌شه.
2. **جلوگیری از ثبت‌نام تکراری** — موقع ثبت‌نام، چهرهٔ جدید با تمام اعضای قبلی مقایسه می‌شود؛ اگر تطبیق پیدا شد (چه با همون اسم، چه با اسم دیگر) ثبت‌نام رد می‌شود، چون خودِ چهره کلید واقعی جلوگیری از ثبت تکراریه (نه فقط اسم، که می‌تونه دستکاری بشه).
3. **تب «اعضا» در پنل پذیرش** — لیست کامل اعضا با جستجو بر اساس نام/تلفن/کد عضویت، به‌همراه وضعیت زندهٔ «داخل باشگاه / خارج شده».
4. **ثبت ورود/خروج متناوب** — قبلاً هر تردد فقط یک رکورد عمومی بود؛ الان اگر یک عضو با فاصلهٔ بیش از ۵ دقیقه دوباره دیده بشه، بین `ورود` و `خروج` جابه‌جا می‌شود (و این وضعیت بعد از ری‌استارت سرویس هم از دیتابیس بازیابی می‌شود، نه فقط در حافظه).
5. **دکمهٔ حذف عضو** در تب اعضا — همراه با تاریخچهٔ تردد و عکسش، و رفرش آنی کش تشخیص چهره تا دوربین بلافاصله دیگه اون فرد رو نشناسه.
6. **کد عضویت خودکار** — دیگه اپراتور چیزی تایپ نمی‌کنه؛ یک عدد ۶ رقمی تصادفیِ یکتا موقع ثبت‌نام تولید می‌شه (اعضای قدیمی بدون کد هم خودکار یکی می‌گیرن).
7. **Webhook + polling برای یکپارچگی با سرور دیگر** — به بخش زیر ببینید.
8. **تشخیص چند-نمونه‌ای (چند زاویه/نور برای هر عضو)** — جدول جدید `member_face_samples`؛ دکمهٔ «عضو موجود است» در صف انتظار برای اضافه‌کردن دستی یک نمونهٔ جدید به یک عضو موجود، به‌جای ثبت‌نام تکراری. جزئیات در بخش «ساختار دیتابیس» بالا.

## یکپارچه‌سازی با یک سرور دیگر (ورود/خروج به‌صورت زنده)

هر عضو یک `membership_code` عددی ۶ رقمی دارد که **خودِ سیستم موقع ثبت‌نام تصادفی تولید می‌کند** (اپراتور چیزی وارد نمی‌کند). این کد، شناسه‌ای هست که باید در سرور دیگرتان هم برای شناسایی افراد استفاده کنید — نه `id` داخلی دیتابیس.

دو راه برای گرفتن اطلاعات ورود/خروج وجود دارد که مکمل هم هستند:

### ۱. Webhook (توصیه‌شده، فوری)

با تنظیم دو متغیر محیطی، به‌ازای هر ورود/خروج فوراً یک `POST` به سرور شما ارسال می‌شود:

```bash
cp .env.example .env
# سپس .env را ویرایش کنید:
# WEBHOOK_URL=http://<آی‌پی سرور شما>:<پورت>/gym-events
# WEBHOOK_SECRET=یک-رشته-تصادفی-طولانی
```

`docker-compose.yml` این دو متغیر را خودکار از `.env` می‌خواند و به کانتینر پاس می‌دهد. بدنه‌ی درخواست این شکلی است:

```json
{
  "event_id": 42,
  "user_id": 7,
  "membership_code": "482913",
  "full_name": "علی رضایی",
  "event_type": "in",
  "checkin_at": "2026-08-29T10:15:03.221000+00:00"
}
```

اگر `WEBHOOK_SECRET` را تنظیم کرده باشید، هر درخواست یک هدر `X-Webhook-Signature: sha256=...` هم دارد (امضای HMAC-SHA256 روی بدنه‌ی خام JSON با همان secret). سرور شما باید این امضا را قبل از پردازش، دوباره محاسبه و مقایسه کند تا مطمئن شود درخواست واقعاً از این سیستم آمده:

```python
import hmac, hashlib

def verify(raw_body: bytes, signature_header: str, secret: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature_header)
```

اگر سرور شما لحظه‌ای در دسترس نباشد، ۳ بار با فاصله‌ی نمایی (۲، ۴ ثانیه) دوباره تلاش می‌شود؛ بعد از آن، رویداد را از دست نمی‌دهیم — همچنان در دیتابیس هست و از طریق روش polling زیر قابل بازیابیه.

### ۲. Polling پشتیبان (`since_id`)

برای اطمینان کامل (یا اگر اصلاً webhook نمی‌خواهید)، سرور شما می‌تواند دوره‌ای این را صدا بزند:

```
GET /api/attendance?since_id=<آخرین id دیده‌شده>&limit=100
```

نتیجه، رویدادهای جدیدتر از `since_id` را از قدیم به جدید برمی‌گرداند — همان شکل JSON بالا، فقط داخل یک آرایه. کافیه بزرگ‌ترین `id` دریافتی رو نگه دارید و دفعه‌ی بعد همونو به‌عنوان `since_id` بفرستید؛ هیچ رویدادی نه گم می‌شود نه دوبار پردازش می‌شود. برای شروع (اولین‌بار) `since_id=0` بفرستید.

> ⚠️ این endpoint فعلاً بدون authentication است (چون قرار بود فقط پنل داخلی صداش بزنه). چون سرور دیگرتون توی همون شبکه‌ی محلیه فعلاً مشکلی نیست، ولی اگه بعداً خواستید از بیرون از شبکه هم بهش دسترسی بدید، حتماً قبلش یه API key ساده اضافه کنیم.

## نصب

```bash
python3 -m venv venv
source venv/bin/activate        # ویندوز: venv\Scripts\activate
pip install -r requirements.txt
```

⚠️ **نکتهٔ مهم دربارهٔ `face_recognition`**: این کتابخانه روی `dlib` بنا شده که از سورس کامپایل می‌شود و به `cmake` + یک کامپایلر C++ نیاز دارد. قبل از `pip install -r requirements.txt`:

- **اوبونتو/دبیان:** `sudo apt install cmake build-essential libopenblas-dev liblapack-dev`
- **ویندوز:** نصب "Desktop development with C++" از Visual Studio Build Tools ساده‌تر است، یا از ویل‌ (wheel) پیش‌کامپایل‌شدهٔ dlib استفاده کنید.
- کامپایل ممکن است چند دقیقه طول بکشد؛ این طبیعی است.

## اجرا با Docker

پروژه یک `Dockerfile` (چندمرحله‌ای، چون کامپایل dlib سنگینه) و یک `docker-compose.yml` آماده دارد.

```bash
docker compose up --build -d
docker compose logs -f     # دیدن لاگ‌ها، از جمله خطای احتمالی دوربین
```

بعد از بالا آمدن: پنل روی `http://localhost:8000/panel/` و مستندات API روی `http://localhost:8000/docs`.

### ⚠️ نکتهٔ حیاتی: دسترسی داکر به وب‌کم

این مورد مهم‌ترین محدودیتِ اجرای این پروژه با Docker است و باید قبل از دیپلوی بدانید:

- **لینوکس (توصیه‌شده برای production):** داکر با فلگ `devices` در `docker-compose.yml` مستقیم به `/dev/video0` روی هاست دسترسی پیدا می‌کند و کار می‌کند. با `ls /dev/video*` روی هاست مطمئن شوید مسیر درست است (اگر متفاوت بود، هم در `docker-compose.yml` و هم مقدار `CAMERA_INDEX` را عوض کنید).
- **مک (macOS):** Docker Desktop داخل یک ماشین مجازی اجرا می‌شود و passthrough مستقیم وب‌کم USB/داخلی را **پشتیبانی نمی‌کند** — این محدودیت خود Docker Desktop است، نه این پروژه. برای توسعه روی مک، پروژه را مستقیم با `python run.py` (بدون داکر) اجرا کنید؛ از داکر فقط برای دیپلوی نهایی روی سرور/PC لینوکسی کنار دوربین استفاده کنید.
- **ویندوز:** مشابه مک، Docker Desktop استاندارد passthrough وب‌کم ندارد. راه‌حل‌های نیمه‌پیشرفته‌ای مثل ابزار [`usbipd-win`](https://github.com/dorssel/usbipd-win) برای اتصال دستگاه USB به WSL2 وجود دارد، ولی برای production همچنان یک PC لینوکسی کنار دوربین ساده‌تر و پایدارتر است.

خلاصه: **معماری این سیستم ("سرور کنار دوربین") ذاتاً برای یک هاست لینوکسی طراحی شده** — چه با Docker چه بدون آن. اگر قصد دارید Docker را روی همان PC لینوکسی که دوربین به آن وصل است اجرا کنید (رایج‌ترین حالت برای این نوع سیستم)، همه‌چیز مثل بالا کار می‌کند.

### پایداری داده‌ها (Volume)

پوشهٔ `./data` روی هاست به `/app/data` داخل کانتینر مپ شده و شامل `gym_face.db` و عکس‌های `static/` است. با `docker compose down` یا rebuild کردن ایمیج، این داده‌ها از بین نمی‌روند. برای پاک‌سازی کامل (مثلاً شروع دوباره از صفر):

```bash
docker compose down
rm -rf ./data
docker compose up --build -d
```

## آماده‌سازی و push به GitHub

پوشه از قبل با `git init` آماده شده و یک `.gitignore` مناسب دارد (دیتابیس، عکس‌های ذخیره‌شدهٔ چهره، `venv/`، و غیره را کنار می‌گذارد — این‌ها داده‌های واقعی کاربران هستند و نباید وارد کنترل نسخه شوند). برای اتصال به یک ریپوی واقعی روی گیت‌هاب:

```bash
git add -A
git commit -m "Initial commit: gym face check-in system"

# روش ۱: با GitHub CLI (ساده‌ترین، هم ریپو رو می‌سازه هم push می‌کنه)
gh repo create gym-face-checkin --private --source=. --remote=origin --push

# روش ۲: دستی (بعد از ساخت ریپوی خالی در وب‌سایت گیت‌هاب)
git remote add origin git@github.com:USERNAME/gym-face-checkin.git
git branch -M main
git push -u origin main
```

⚠️ **قبل از public کردن ریپو**: مطمئن شوید `data/` و `gym_face.db` هیچ‌وقت commit نشده‌اند (`.gitignore` این کار را می‌کند، ولی یک بار با `git status` چک کنید) — این فایل‌ها شامل تصاویر و بردارهای بیومتریک اعضای واقعی باشگاه هستند.

## نکات تنظیم (`app/config.py`)

| پارامتر | پیش‌فرض | توضیح |
|---|---|---|
| `CAMERA_INDEX` | 0 | اگر چند دوربین دارید عوض کنید |
| `PROCESS_EVERY_N_FRAMES` | 5 | بالاتر = مصرف CPU کمتر ولی تأخیر تشخیص بیشتر |
| `KNOWN_USER_TOLERANCE` | 0.5 | پایین‌تر = سخت‌گیرانه‌تر برای تشخیص عضو (کمتر false-positive) |
| `PENDING_DEDUP_TOLERANCE` | 0.58 | آستانهٔ «همون فرد ناشناس هنوز جلوی دوربینه» — کمی سهل‌گیرانه‌تر از تشخیص عضو، چون false-positive اینجا فقط یعنی یک عکس تکراری رد شده، نه اشتباه هویتی |
| `PENDING_DEDUP_MAX_SAMPLES` | 5 | چند نمونهٔ اخیر برای هر فرد در صف نگه داشته شود تا تغییر تدریجی زاویه/حالت چهره باعث تشخیص اشتباهِ «فرد جدید» نشود |
| `REGISTRATION_DUPLICATE_FACE_TOLERANCE` | 0.5 (برابر با `KNOWN_USER_TOLERANCE`) | آستانهٔ جلوگیری از ثبت‌نام تکراری همون فرد در سیستم |
| `PENDING_DEDUP_WINDOW_SECONDS` | 120 | همون بازهٔ ۲ دقیقه‌ای آنتی‌اسپم که در بریف خواسته شده بود |
| `ATTENDANCE_COOLDOWN_SECONDS` | 300 | برای جلوگیری از ثبت چندبارهٔ تردد یک عضو در چند ثانیه — این مورد در بریف نبود، بر اساس منطق اضافه شد |
| `MAX_FACE_SAMPLES_PER_MEMBER` | 8 | حداکثر تعداد نمونه چهره به ازای هر عضو (`member_face_samples`)؛ اگر در عمل کم بود، همین عدد را افزایش دهید |
| `MEMBERSHIP_CODE_DIGITS` | 6 | تعداد رقم کد عضویت خودکار |
| `WEBHOOK_URL` (env) | خالی = غیرفعال | آدرس سرور دیگر برای دریافت فوری رویدادها |
| `WEBHOOK_SECRET` (env) | خالی = بدون امضا | برای امضای HMAC-SHA256 هر webhook |

این‌ها را حتماً با نور و دوربین واقعی محل تست و کالیبره کنید؛ مقادیر تلورانس بسته به کیفیت دوربین متفاوت عمل می‌کنند.

## محدودیت‌ها و گام‌های بعدی (فاز اول عمداً ساده نگه داشته شده)

1. **بدون احراز هویت روی پنل** — طبق تصمیم فعلی؛ قبل از دیپلوی در شبکهٔ عمومی حتماً لاگین اضافه شود.
2. **یک دوربین / یک پردازش** — برای چند شعبه یا چند دوربین باید هر شعبه یک نمونهٔ جدا (یا صف پیام مثل Redis) داشته باشد.
3. **SQLite تک‌فایلی** — برای زیر ۲۰۰ کاربر و بار ترافیکی یک باشگاه کاملاً کافی است؛ اگر بعداً چند شعبه/سرور همزمان نیاز شد باید به Postgres مهاجرت کرد.
4. **کیفیت تشخیص در نور کم** یا با ماسک/عینک افت می‌کند — این محدودیت خود کتابخانهٔ `face_recognition` (مبتنی بر dlib HOG/CNN) است، نه یک باگ در این پیاده‌سازی.
5. می‌توانید بعداً یک اسکریپت پاک‌سازی (cron) اضافه کنید که ردیف‌های `rejected` قدیمی و عکس‌های متناظرشان را حذف کند تا حجم `static/pending_faces` رشد نکند.

هر بخشی از این کد که بخواهید عمیق‌تر توضیح بدم یا تغییرش بدیم (مثلاً افزودن لاگین اپراتور، چند دوربین، یا گزارش‌گیری تردد) بگو تا ادامه بدیم.
